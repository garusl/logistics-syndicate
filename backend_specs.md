Техническое Задание (ТЗ): Backend-архитектура Logistics Syndicate

1. Технологический стек

Для обеспечения высокой скорости работы таймеров и надежности финансовых транзакций выбран следующий стек:

Язык и Фреймворк: Node.js + NestJS (обеспечивает строгую типизацию через TypeScript и удобную модульную архитектуру).

Основная База Данных (БД): PostgreSQL 15+ (строгое соблюдение ACID для всех операций с балансом).

In-Memory хранилище и Очереди: Redis (кэширование сессий, хранение активных таймеров рейсов, защита от спам-запросов).

ORM: Prisma или TypeORM (для удобной миграции и работы со связями в БД).

2. Схема Базы Данных (PostgreSQL)

Ниже описаны ключевые таблицы и их критические поля.

Таблица users (Пользователи)

Основа экономики. Хранит балансы и ограничения.

id (UUID, Primary Key)

login, password_hash, email

role (enum: F2P, VIP, ADMIN)

balance_bucks (BigInt) - Игровая валюта (Soft Currency).

balance_diamonds (Decimal) - Выводная валюта (Hard Currency).

last_energy_update (Timestamp) - Время последнего списания/начисления энергии для динамического расчета.

invited_by (UUID) - ID рефовода (для Партнерской программы).

Таблица trucks (Автопарк)

Привязка купленных машин к игрокам.

id (UUID, PK)

Таблица active_trips (Активные рейсы)

Связующая таблица для таймеров.

id (UUID, PK)

status (enum: IN_PROGRESS, COMPLETED, FAILED)

3. Логика работы ядра (Core Logic)

3.1. Механика таймеров (Рейсы)

В браузерных играх нельзя доверять таймерам на стороне клиента (браузера), так как игрок может ускорить время через Cheat Engine или подмену пакетов.
Реализация:

Игрок нажимает "Взять груз".

Сервер проверяет: есть ли машина, свободна ли она, хватает ли бензина и энергии.

Сервер списывает бензин и энергию, создает запись в active_trips с точным end_time (Текущее время + длительность рейса).

Задание ставится в Redis Queue (очередь отложенных задач BullMQ) с задержкой, равной длительности рейса.

По истечении таймера Redis вызывает Worker (обработчик), который меняет статус на COMPLETED.

Клиент только запрашивает у сервера текущее состояние таймера и отрисовывает полоску прогресса.

3.2. Динамическая генерация энергии (Бодрости)

Чтобы не делать ежесекундный апдейт базы для 10 000 игроков, энергия рассчитывается "на лету" (On-the-fly calculation):

Формула: Текущая Энергия = MIN(100, Базовая Энергия + ((Текущее время - last_energy_update) * Скорость_регена))

Запись в БД происходит только в момент траты энергии (взятие рейса).

4. Архитектура Безопасности и Анти-чит

Это самый важный раздел проекта. Любая уязвимость приведет к бесконечному созданию "Бриллиантов" и кассовому разрыву.

4.1. Транзакционная целостность (Защита от дюпов/Double-Spend)

Игрок может попытаться отправить 10 запросов на покупку VIP-тягача за миллисекунду, надеясь, что сервер спишет деньги 1 раз, а выдаст 10 машин (Race Condition).
Решение: Обязательное использование SELECT ... FOR UPDATE в PostgreSQL при любых финансовых операциях. Это блокирует строку пользователя в БД на время выполнения транзакции.

4.2. Rate Limiting (Защита от автокликеров)

Используем Redis Rate Limiter.

Ограничения на эндпоинты (API):

/api/game/job/take — не более 1 запроса в 3 секунды.

/api/bank/exchange — не более 1 запроса в 10 секунд.

При превышении лимитов пользователю возвращается HTTP код 429 Too Many Requests. Повторные нарушения помечают аккаунт флагом для ручной проверки (Shadowban).

4.3. Блокировка мультиаккаунтов (Фермы ботов)

Ботоводы создают цепочки рефералов сами под себя, чтобы получать бонусные Бриллианты.
Решение:

Сбор отпечатков браузера (Browser Fingerprinting) на клиенте (Canvas API, WebGL, User-Agent) + фиксация IP подсети.

Логика на сервере: Если игрок пытается зарегистрироваться по реферальной ссылке пользователя с таким же Fingerprint / IP подсетью — бонус отменяется, а оба аккаунта ставятся на контроль.

Обязательная ручная модерация первой заявки на вывод Бриллиантов.

5. Экономические предохранители (Kill Switches)

В Backend должна быть встроена панель управления для Project Manager (Админка), содержащая "Красные кнопки":

Динамический налог сервера: Администратор может ползунком изменить системный налог на бензин от 10% до 50%, чтобы быстро "сжечь" лишние Баксы у населения, если инфляция выйдет из-под контроля.

Заморозка Банка: Временное отключение эндпоинта обмена Баксы -> Бриллианты при обнаружении аномальной активности (пока идет разбирательство).

Плавающий шанс Осколка: Шанс выпадения Осколка должен динамически снижаться, если резервный фонд выплат проекта падает ниже критической отметки (например, ниже $500).
